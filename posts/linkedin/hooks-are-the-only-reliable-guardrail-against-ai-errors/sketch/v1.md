Eu não confio em nenhuma regra que só existe no system prompt.

Não é implicância com prompt. É estatística.

O system prompt é o que mais rende por hora de trabalho. Ele tira o modelo de "não faço ideia do formato que você quer" e coloca em 99% de acerto. Isso é muito.

E se você é o usuário, 99% é invisível: você lê a resposta, vê que saiu torta, manda de novo. Você é o loop.

Uma aplicação não tem você no loop.

O mesmo prompt roda mil vezes antes do almoço. A 99%, são dez saídas quebradas por dia, e ninguém olha nenhuma delas.

E essa é a conta otimista, porque agente não é uma chamada só. É uma cadeia. Seis passos a 99% cada dão 94% de ponta a ponta.

Uma a cada dezessete execuções sai errada em algum lugar. E o erro raramente aparece como erro: aparece três passos depois, como um campo vazio que alguém leu como zero.

A resposta óbvia é "tenta de novo". Só que tentar de novo sem dizer o que quebrou é sortear na mesma distribuição outra vez. O que conserta não é a tentativa, é o erro que vai junto com ela.

É isso que um hook é: código entre a saída do modelo e quem consome ela. Ele valida, e quando falha devolve o erro literal para o modelo, antes que qualquer outro passo veja aquilo.

Não "por favor siga o formato". "Campo due_date: 'próxima terça' não é uma data válida."

Isso já vem pronto nos frameworks. No Pydantic AI você levanta um ModelRetry no output validator e a mensagem volta para o modelo. No SDK do Claude Code é o PreToolUse, que barra a tool call antes de acontecer e explica por quê.

E aqui entra a confusão mais comum: structured output não é hook. Constrained decoding garante que o JSON parseia e que o enum é um dos valores que você listou.

Não garante que o ID existe no seu banco, nem que o valor bate com o que foi pedido. Formato dá para restringir na hora de gerar. Verdade não dá.

Agora a parte cara.

Escrever o hook obriga você a definir o que é "certo" em código, e é aí que a maioria trava. Não porque validar é difícil, mas porque ninguém nunca decidiu. O prompt aceitava a ambiguidade. O validator não.

Cada rejeição é uma ida e volta a mais: latência e tokens que você não estava contando.

E ele precisa de teto. Hook sem limite de tentativa numa regra que o modelo não consegue cumprir é loop infinito com fatura.

Quando estoura, tem que existir um caminho de verdade: falhar alto, escalar para um humano, jogar numa fila de erro. O que não pode é passar quieto.

E o hook só pega o que dá para checar em código. Schema, enum, existência, permissão, arquivo em disco. Ele não sabe se a resposta está certa.

Uma resposta bem formada, validada em todos os campos e completamente errada passa por qualquer hook.

Então você termina com dois tipos de regra: as que o código garante e as que você reza. Continua tendo as duas. A diferença é que agora você sabe quais são quais, e escolhe de que lado cada uma fica.
